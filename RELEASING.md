# BTTV Android CE — build validation and release preparation

BTTV Android CE is an unofficial community-maintained continuation of the
original MIT-licensed BTTV Android project. Its public source and release
repository is [WhiteTree97/bttv-android-ce](https://github.com/WhiteTree97/bttv-android-ce).
Published CE beta releases are listed on the [releases page](https://github.com/WhiteTree97/bttv-android-ce/releases),
which includes prereleases; do not direct CE users to the original project's downloads.

This document describes maintainer gates, not permission to publish a release.
The application remains `tv.twitch.bttvandroid.app`, version `0.43.2-beta`,
versionCode `1208000338`, minSdk 29 and targetSdk 36. No version bump is implied.

## Reproducible inputs and isolated builds

Follow the [Docker or manual instructions](README.md#build-it-yourself).
`tools/prepare_twitch_input.py` checks the five root-level APK payloads against
the pinned hashes in `tools/twitch-31.2.0-inputs.json`. It does not download them
or accept arbitrary APKMirror variants just because their versionName matches.
Its optional `--armv7-bundle` selects only the pinned ARMv7 APK from a second
bundle while preserving all four pinned primary APKs. It never substitutes the
secondary base or density/ARM64 components.
Keep Twitch inputs, decoded trees, APK exports, credentials and caches out of Git.

`tools/build_production.py` copies tracked production inputs, plus its explicit
infrastructure inputs, into a new workspace. It excludes temporary notification,
purchase and other untracked diagnostics. Windows shell line endings are normalized
only in that staged copy. The normal `initworkspace` flow runs there, with a
fresh disassembly and writable Gradle project. The checkout is not a build target.

Docker Compose selects `linux/amd64` for the Linux SDK/build-companion executables
and builds the local Java 11 toolchain instead of assuming a previously
published upstream image contains this port. It installs SDK Build Tools 30.0.3
and android-30, Apktool 2.9.3, APKEditor 1.4.9, Uber APK Signer 1.2.1, Baksmali
2.4.0 and build-companion 5.2.0. The JAR/executable hashes are checked in Dockerfile.
Gradle 7.2 and AGP 4.1.3 remain unchanged. The mod's compilation SDK is distinct
from the patched application's minSdk/targetSdk values.

Manual Linux/WSL builds require SDK and build-tool installation paths without
spaces or other whitespace because the inherited scripts do not support them.
Choose these paths before configuring the tools; the standard Docker paths are unchanged.

Fresh toolchain/dependency downloads require their official repositories to be
reachable. Existing dependency caches may be reused; decoded/patched caches must
not substitute for a fresh build. Export destinations must be new. Never overwrite
an accepted APK/archive while validating infrastructure.

## Local checks and artifact verification

```bash
python3 tests/stage9_infrastructure.py
for script in initworkspace disassemble buildsource build patch tools/docker_build.sh; do bash -n "$script"; done
git diff --check
```

The infrastructure suite checks input validation, original README assets/credits,
notice coverage, patch syntax, build isolation and release metadata failure cases.
It is not a replacement for the feature JVM suites or physical-device validation.

The build wrapper verifies the completed APK before copying it to the requested
output directory. `tools/verify_release_apk.py` uses SDK `aapt`, `apksigner` and
`zipalign`, plus independent ZIP CRC/duplicate, DEX checksum/pool and native ELF/
alignment checks. It requires seven contiguous DEX files, the dual-ARM 39+39
native sets, unchanged original Twitch native payloads, the permanent package/
version/SDKs, nine distinct providers and bundled notice resources. It rejects
temporary notification instrumentation. Smali assembly is not an ART runtime test.

## Signing continuity — decision required before public distribution

The accepted experimental APKs use the publicly bundled signing-tool debug identity:

`1E08A903AEF9C3A721510B64EC764D01D3D094EB954161B62544EA8F187B5953`

That key is not a secure public-release publisher identity. A mathematically valid
signature does not establish exclusive key custody. Local builds without `KS`
explicitly remain test builds. The artifact verifier permits that certificate only
with `--allow-test-key`; release metadata generation refuses it.

Private release keys belong outside the Git repository. No key is generated by
these scripts. Keep the currently tested package/version unchanged until a
separate release/version decision is approved.

### Existing settings and the protected signing stage

Historically `KS` selected an external keystore, and `KSPASS` was passed as both
store/key passwords to Uber APK Signer under alias `bttv-android`. With no `KS`,
the signer used its public debug key. The wrapper optionally compared the final
certificate with `EXPECTED_SIGNER_SHA256`.

Private releases now use two distinct stages:

1. `tools/build_production.py --unsigned` produces **unsigned.apk + unsigned.json**,
   never a verified release. No signing inputs may enter that build process.
2. `tools/sign_release.py` runs separately, preferably in an offline read-only
   SDK container, after the build has exited. It aligns first with SDK 30.0.3
   `zipalign -p 4`, signs with SDK `apksigner`, then runs the unchanged complete
   `verify_release_apk.py` checks before exporting **twitch.apk + verification.json**.
   Gradle, project shell scripts and application bytecode are not run there.

Signing settings (supplied only to stage 2):

| Setting | Meaning |
| --- | --- |
| `KS` | Existing absolute external PKCS12/JKS file, outside the source repository and output directory; mount read-only in Docker. |
| `KSPASS_FILE` | Preferred: existing absolute external UTF-8 password file, without BOM, one nonempty line (optional LF/CRLF). Treat it as a secret and mount read-only. |
| `KSPASS` | Compatibility alternative to the file, never both. SDK arguments contain only `env:KSPASS`, not its value. Avoid Docker environment secrets where file mounts suffice. |
| `EXPECTED_SIGNER_SHA256` | Required 64 hex characters, without colons, for the approved certificate. Public debug identity is rejected. This fingerprint is public policy, not a private key. |
| `ANDROID_SDK_ROOT` / `--sdk` | Existing SDK with Build Tools 30.0.3. No substitute toolchain or generated key is selected automatically. |

The fixed key alias remains **bttv-android**, and store/key passwords must be the
same. The signer first tries the store password for the key; stdin is closed, so
a different key password fails instead of prompting. A one-line password file
is not supplied twice. PKCS12 with the procedure below satisfies that convention. Local builds
with no signing inputs retain the existing public debug identity; direct
`build`/production-build invocations with private signing inputs now fail before
building instead of silently falling back or passing passwords in argv. Do not
put signing settings in the repository `.env`. Keep secrets outside source,
image build contexts, console commands, logs, test fixtures and artifacts.

Android upgrades and the in-app updater require signing compatibility. The updater
requires exact installed/downloaded certificate equality. A new private key cannot
transparently update existing debug-signed installations. Plan that bootstrap
separately; do not relax verification or promise a data-preserving overlay.

### Windows: user-run key generation (instructions only)

Use an installed official JDK 11's `keytool.exe`, matching the build toolchain;
set `JAVA_HOME` to that JDK first.
Run these commands yourself in PowerShell. Do not use a recorded/transcribed
session, supply passwords as command arguments, or paste them into source/logs.
The directory below must be NEW, outside the checkout, and on a private local disk.

```powershell
$keytool = Join-Path $env:JAVA_HOME 'bin\keytool.exe'
if (!(Test-Path -LiteralPath $keytool)) { throw 'Install/select an official JDK first.' }
$keyDir = Join-Path $env:USERPROFILE '.bttv-community-signing'
if (Test-Path -LiteralPath $keyDir) { throw 'Choose a new private directory; do not overwrite existing keys.' }
New-Item -ItemType Directory -Path $keyDir | Out-Null
$identity = [System.Security.Principal.WindowsIdentity]::GetCurrent().Name
& icacls.exe $keyDir /inheritance:r /grant:r ("{0}:(OI)(CI)F" -f $identity)
if ($LASTEXITCODE -ne 0) { throw 'Could not restrict the directory ACL.' }
$keyPath = Join-Path $keyDir 'community-release.p12'
& $keytool -genkeypair -keystore $keyPath -storetype PKCS12 `
  -alias bttv-android -keyalg RSA -keysize 4096 -sigalg SHA256withRSA -validity 10000
if ($LASTEXITCODE -ne 0) { throw 'Key generation failed; inspect privately before retrying.' }
& $keytool -list -v -keystore $keyPath -alias bttv-android
```

Keytool prompts privately for the store password and certificate identity. Choose
and retain a strong ASCII password without line breaks, use that same password
for the key, and choose the certificate subject deliberately (it will be public).
The command does not prescribe final branding, owner identity or repository name.
Record the **certificate SHA256** from the final listing, removing colons, as the
expected fingerprint. Do not confuse it with the keystore file's SHA-256.
Back up the encrypted keystore offline and retain the password separately in a
password manager; losing the key prevents compatible future updates.

For a future local signing run, create a temporary password file in that restricted
directory from the SAME password (this writes a secret file, not a generated key):

```powershell
$passPath = Join-Path $keyDir 'signing.password'
if (Test-Path -LiteralPath $passPath) { throw 'Do not overwrite an existing secret file.' }
$securePassword = Read-Host 'Existing keystore password' -AsSecureString
$passwordPointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
try {
  $plainPassword = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($passwordPointer)
  if (!$plainPassword -or $plainPassword.Contains("`r") -or $plainPassword.Contains("`n")) { throw 'Use one nonempty line.' }
  [IO.File]::WriteAllText($passPath, $plainPassword, [Text.UTF8Encoding]::new($false))
} finally {
  [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($passwordPointer)
  Remove-Variable plainPassword, securePassword -ErrorAction SilentlyContinue
}
```

The file is plaintext protected by the parent ACL: keep it only for the signing
session and remove it yourself afterward. Do not create it under the Git checkout
merely because `.gitignore` also guards common private-key/password extensions.

### Future local Docker invocation

Build/review the toolchain first, without keys. Select fresh unsigned and signed
output directories; examples below must not overwrite accepted archives. The
following is a future USER-RUN build/sign procedure, not an action performed by
this infrastructure task:

```powershell
$repo = 'C:\BTTV\bttv'
$unsignedOut = Join-Path $repo 'dist\unsigned-new'
$signedOut = Join-Path $repo 'dist\signed-new'
if ((Test-Path $unsignedOut) -or (Test-Path $signedOut)) { throw 'Choose new output directories.' }
New-Item -ItemType Directory -Path $unsignedOut, $signedOut | Out-Null
docker build --tag bttv-builder:community $repo
if ($LASTEXITCODE -ne 0) { throw 'Toolchain build failed.' }
docker run --rm --entrypoint python3 `
  --mount "type=bind,source=$repo,target=/source,readonly" `
  --mount "type=bind,source=$unsignedOut,target=/output" `
  bttv-builder:community /source/tools/build_production.py `
  --input /source/twitch.zip --workspace /tmp/bttv-build --output /output/build --unsigned
if ($LASTEXITCODE -ne 0) { throw 'Unsigned preparation failed.' }
# Supply the public certificate fingerprint obtained above; never put a password here.
$env:EXPECTED_SIGNER_SHA256 = Read-Host 'Approved certificate SHA256 (64 hex characters, no colons)'
docker run --rm --network none --read-only --tmpfs /tmp:rw,nosuid,size=2g --entrypoint python3 `
  --mount "type=bind,source=$repo,target=/source,readonly" `
  --mount "type=bind,source=$signedOut,target=/output" `
  --mount "type=bind,source=$keyPath,target=/run/keystore.p12,readonly" `
  --mount "type=bind,source=$passPath,target=/run/password,readonly" `
  -e KS=/run/keystore.p12 -e KSPASS_FILE=/run/password -e EXPECTED_SIGNER_SHA256 -e PYTHONDONTWRITEBYTECODE=1 `
  bttv-builder:community /source/tools/sign_release.py `
  --apk /source/dist/unsigned-new/build/unsigned.apk --input /source/twitch.zip --output /output/build
if ($LASTEXITCODE -ne 0) { throw 'Signing/verification failed; do not use the output.' }
```

Only a successful verifier/export authorizes calling that output a signed
candidate. Publication, archive promotion, version approval and device acceptance
remain separate. Never substitute the unsigned intermediate for a release APK.

## CI boundaries and maintainer provisioning

PR checks and the Docker-validation workflow receive no signing inputs and cannot
publish. Signing is opt-in through repository variable
`COMMUNITY_SIGNING_ENABLED=true`, **workflow_dispatch only**, and the exact default
branch (not a hardcoded original repository or master branch). Both preparation
and signing assert that `GITHUB_REPOSITORY` equals the canonical
`UpdateSource.REPOSITORY`; the provisional name is not duplicated in CI.
Checkout is pinned to the dispatch's exact commit, and Actions use reviewed full
commit pins. The token has only `contents: read`; no release/tag/push step exists.

Before enabling CI, an administrator MUST create **community-release**:

- Restrict deployments to the exact protected default branch, not arbitrary
  branches/tags; review changes to that branch, workflows and signing tools.
- Require a trusted reviewer, prevent self-review and disable administrator bypass.
  If that independent review is unavailable, keep CI signing disabled and use an
  authorized local offline signing process instead.
- Store `KEYSTORE` (base64 of the USER-GENERATED encrypted keystore) and `KSPASS`
  ONLY as environment secrets. Do not duplicate them as repository/organization
  secrets accessible to another workflow.
- Set environment variable `RELEASE_SIGNER_SHA256` to the approved public pin.
- Set repository variable `TWITCH_31_INPUT_URL` to an authorized, non-secret HTTPS
  URL for the pinned input, without credentials, query tokens or a fragment.
  Repository variables are not secrets. If no permitted source can be exposed
  this way, leave CI disabled and use local inputs; private input retrieval needs
  a separate design. No source inputs are hosted/committed by these changes.
- Configure the final repository identity in UpdateSource before enabling signing.

YAML cannot create or prove these remote protection settings. A referenced
nonexistent environment may be created unprotected by GitHub; never add keys until
its reviewer/branch rules are independently checked. No environment, secret or
repository variable is created or changed by this task.

The unsigned job has no secret references or key mounts. Its artifact is bound to
the current workflow/commit, retained for one day, and reviewed before the protected
signing job starts. Signing uses a separate fresh hosted runner; all downloads and
SDK image preparation precede secret materialization. Keys/passwords are created
with 0700/0600 permissions under RUNNER_TEMP, outside checkout, then mounted read-only
into the offline signing container. No Gradle/build step sees them. Cleanup runs
on success or failure before uploading only the verified APK and proof (3-day
retention). Ephemeral runner teardown handles interrupted jobs; do not replace the
hosted runner with a persistent self-hosted runner without a separate security review.

Environment protection availability depends on repository visibility and GitHub
plan. Confirm it before storing any key. This preparation adds no publishing
workflow, changes no remotes and requires no write-capable GitHub token.

## Future updater-compatible release metadata

Community-fork automatic and manual checking use the same release source. Change
the single `UpdateSource.REPOSITORY` literal in
`mod/app/src/main/java/bttv/updater/UpdateSource.java` only if the release repository
is intentionally migrated; the current CE repository is `WhiteTree97/bttv-android-ce`.
`tools/release_metadata.py` reads that exact literal too; there is no separate
publisher URL setting. Rebuild clients after changing it. There is no fallback
to the original project's releases. Original upstream attribution is retained.

Discovery uses `https://api.github.com/repos/OWNER/REPO/releases?per_page=10&page=N`,
not `/releases/latest`, which excludes prereleases. Both stable and beta/prerelease
releases are eligible, but drafts are never offered. The updater checks up to
three pages (30 recent releases), with existing per-response byte/depth limits,
timeouts, cancellation and rate-limit handling. It never follows an API `Link`
header to an arbitrary URL. Keep the intended compatible release within this
window; discovery does not promise to search the repository's entire history.

Every candidate passes the same compatibility/asset metadata checks before an
offer. The highest compatible, strictly newer **versionCode** in the window wins,
regardless of tag ordering, publication order or prerelease status. Incompatible
or malformed entries cannot become offers; conflicting highest-code assets fail
closed. GitHub `prerelease: true` does not bypass package, SDK, dual-ARM, signer,
SHA-256, size or version checks. Metadata checks never install an APK; downloading
and installation require user confirmation. Downloads must originate at the
configured repository's exact HTTPS release asset URL. Only the existing GitHub
asset CDN hosts are accepted as redirects; arbitrary hosts/repositories are not.

Before an end-to-end update test, choose the final public repository and install
a baseline build containing this configuration. Existing upstream-only clients
do not switch sources merely because a community release is published. Choose
the repository before distributing that baseline: a later rename/redirect to a
different repository is intentionally rejected by the allowlist.

The baseline and candidate must have the same package and approved signing
identity, and the candidate must have a strictly higher approved versionCode.
No signing-key transition is authorized or implemented here. The metadata tool
continues to reject the known public test/debug signing identity; a successful
test-signed local build is not evidence of production signing readiness. Do not
disable that gate to publish a release. Signing decisions and any migration from
existing test installations require separate approval.

After separately authorized build/upload/publication, verify both manual and
automatic discovery against the real release, download/hash/signature checks,
user-confirmed overlay installation and data preservation. Also test draft,
wrong-signer/package, stale-code and cancelled-download rejection. No release
workflow or publication is performed by the metadata tool.

Before a future release, obtain explicit approval for a versionName/tag and a
strictly increasing versionCode. The present name/tag already refers to an old
upstream release and the current code must not be reused as a newer update. Do
not infer approval for `0.44` or choose a new code automatically.

After an approved APK has been uploaded to an authorized draft release, save the
actual release API response as `release.json`. Only then is the final asset ID
known. The local-only metadata tool independently re-verifies the actual APK:

```bash
python3 tools/release_metadata.py --help
```

Supply `--apk`, `--input`, `--expected-signer`, `--release-json`,
`--previous-code` and a new `--output` path. The previous code is the highest
supported installed code, not an invented smaller value. The tool emits one visible
`bttv-update` fenced JSON block and performs no network or publishing action.
It refuses test signing, reused codes, mismatched tag/version, ambiguous assets,
incorrect size/hash and off-origin asset URLs. If GitHub does not provide an asset
digest, independently confirm that the uploaded bytes match the verified local
APK before publication. Preserve ordinary release notes
outside that single block; the uploader must not substitute placeholder asset IDs.

The block includes schemaVersion, standalone, packageName, versionName,
versionCode, releaseTag, signerSha256, minSdk, supportedAbis, twitchVersion,
assetId, assetName, sizeBytes and sha256. The existing app verifies the metadata
and downloaded APK independently. Run the actual updater parser tests and review
the final release JSON before an independently authorized publication. A candidate
artifact or source merge is not proof that a future update installs successfully.

## Notices and remaining release gates

Preserve [THIRD_PARTY_NOTICES.md](THIRD_PARTY_NOTICES.md), the two existing library
NOTICE files, provenance records and both bundled license resources. Verify the
actual exported APK contains them and retains the PSL NOTICE/data. The preferred
PSL source URL/hash and relevant component-specific notices are supplied there.

Notice implementation does not itself settle proprietary Twitch binary
redistribution, provider artwork/service/trademark terms, or all jurisdictional
legal questions. Review those with maintainers before public distribution.
Complete final device coverage (including supported ARMv7/API29 targets and an
authorized same-signer newer-release update), and make signing/versioning decisions
before publication. Historical test observations must not be promoted to universal
device acceptance.

Correction of identities on existing port commits is separately deferred. Do not
rewrite upstream contributors/history as part of release preparation. Any later
authorized rewrite needs a recoverable backup and tree/message/date preservation.
